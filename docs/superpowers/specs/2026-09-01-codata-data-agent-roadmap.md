# Codata Data Agent 二开自研 Roadmap

- 日期：2026-09-01
- 状态：汇报规划稿（供决策评审）
- 汇报对象：管理层 / 产品决策方
- 一句话：基于开源 Codata（桌面 data agent）+ CodataAdmin（成熟语义平台）二开，补齐**团队协作层**这一唯一核心缺口，升级为"团队共用、自主可控"的企业级 data agent；分 2026 MVP 与 2027 完整版两阶段交付。

---

## 0. 概要

- **做什么**：把开源 Codata（桌面 agent）和 CodataAdmin（语义平台）这两套已有系统接起来、补上它们之间的缺口——**团队协作层**，让 data agent 从"个人本地工具"变成"团队共用、分析资产可沉淀、可接力、口径可信"的企业级能力。
- **怎么做**：语义层**不自研**。CodataAdmin 已经是一套跑通的 6 层语义平台，且已作为 MCP server 对接 Codata，登录(OAuth2 脚手架，对接公司统一登录)/RBAC/口径优先/裸 SQL 审计/就绪自检全部现成。因此**自研主体从"造语义层"收窄为"造协作层"**，复用率大幅提升、周期与人力显著下调。
- **两阶段**：
  - **2026 MVP**：协作闭环（共享到团队 + 会话 fork 接力 + 口径标注随共享传递 + 团队搜索）+ 桌面端登录/共享/fork 入口。
  - **2027 完整版**：语义层深化（查询编译引擎、口径库盖章、知识层治理）+ skills 服务化 + 权限化 fork + 治理增强。
- **投入**：MVP 约 2–3 人 / ~8–10 周；完整版约 4–5 人 / 跨年度。
- **复用率**：公司统一登录(OAuth2 脚手架复用)、RBAC、语义层 6 层、MCP 暴露、口径优先、裸 SQL 审计、上游变更治理、就绪自检——全部直接复用 CodataAdmin 现成能力；桌面端分析链路复用 Codata。净新增仅协作层 + 桌面端轻改。
- **风险可控性**：MVP 是在成熟底座上"加一层"，POC 风险低；最大不确定性在 2027 的查询编译引擎（结构化查询自动编译），属可控的演进项。

## 1. 现状盘点

### 1.1 Codata（桌面 data agent，v1.1.23）

- 桌面闭环已跑通：自然语言问数 → 表/指标发现 → SQL 生成执行 → 结果卡 + 图表 → 看板/报告。
- 已有：专家团多 Agent 编排、知识库、MCP 连接器、调度器、插件、技能、记忆、artifact、HTML 数据报告。
- P0「首次可用」已落地：`run_query` 结果行回喂 LLM、口径强制 + 数量级 sanity-check、codata 默认模式 + 空状态引导。
- 角色：**MCP client + 分析消费端**。

### 1.2 CodataAdmin（语义平台 + 管理后台）

栈：FastAPI + SQLAlchemy + Vue3 + TS + Element Plus；主库 MySQL，语义检索副库 PostgreSQL + pgvector；APScheduler + FastMCP。

**已落地能力（经仓库文档与补丁时间线核实）**：

| 能力 | 状态 | 证据 |
|---|---|---|
| 飞书 OAuth 登录（将平移对接公司统一集成登录） | ✅ 已实现（OAuth2 脚手架） | `backend/docs/feishu-oauth.md`（标准 OAuth2 端点，回调自动注册登录）。当前指向飞书，改指向公司统一 IDP 属"换端点+凭据"的轻改，非从零做 |

**CodataAdmin 没有的（= 本次自研缺口）**：

- 团队协作层：共享到团队、会话 fork 接力、fork 溯源/热度、团队分区 + 搜索。
- 口径标注**随共享单元传递**的传播机制（口径优先本身有，但"随共享传递"没有载体）。
- 桌面端的团队登录态、共享/fork 入口。
- skills 集中管理 + 服务端执行（Codata 有 skills，但散在本地；CodataAdmin 无承载）。

## 2. 目标与定位

- **总目标**：把 Codata 从"个人本地 data agent"升级为"团队共用、自主可控"的企业级 data agent，分析资产可沉淀、可接力、口径可信可见。
- **2026 MVP**：协作闭环。证明"团队分析产出能沉淀、能接力、口径随共享可见"。
- **2027 完整版**：语义层深化 + 企业级治理完整。查询可自动编译、口径可盖章复用、skills 服务化、fork 权限化、治理自动化。

## 2.5 路线选择论证：采购第三方 vs 自研整合

> 前提：这里的"自研"不是从零造，而是**整合并增强已有的公司自研资产**（Codata + CodataAdmin 均为存量：Codata 以 Apache-2.0 开源但主导权在我方，CodataAdmin 为内部平台）。因此它天然带"沉没投入已发生、只做边际再投入"的性质；而"采购"是引入一套外部成熟产品替代或覆盖。两条路的风险画像因此高度不对称，需在决策评审时正视各自弊端。

### 2.5.1 采购第三方的弊端与风险

- **数据安全与合规（最重）**：data agent 的本质是"能连库、能执行 SQL、能看结果"。采购 SaaS 意味着核心数据的查询链路、结果、甚至 schema 要出公司边界，合规/安全审查极重，敏感场景可能直接一票否决。即便选私有化/VPC 部署，第三方私有化版本常功能阉割、更新滞后、价格陡增——"安全"与"能力"往往二选一。
- **语义资产与口径主权**：公司最值钱的不是 agent 本身，是**沉淀的口径/指标/语义模型**（CodataAdmin 6 层已在做的事）。采购后这些资产要么迁进供应商语义体系（被绑定），要么迁不进去（白丢）。口径主权交到外部，是战略层面的让渡。
- **供应商锁定与议价权**：业务、看板、口径一旦长在第三方上，迁移成本极高；续费涨价、产品转向、被收购/停服都由不得己。长期是"用可控性换短期省事"。
- **贴合度与定制**：通用产品按大众需求设计，公司特有的业务域、审批流、权限模型、统一登录、内部数仓形态往往对不上；定制要么等供应商排期（慢且贵），要么做不了。
- **成本结构**：表面是订阅费，实际叠加按席位/查询量线性计费、私有化溢价、定制开发费、数据对接实施费、内部对接人力。长期 TCO 未必更低，且是持续性刚性支出。
- **沉没投入浪费**：Codata + CodataAdmin 已投入并跑通（桌面闭环、语义 6 层、MCP、口径、审计）。采购等于把既有资产边缘化甚至废弃，已花的钱和积累的 know-how 打水漂。

### 2.5.2 自研整合的弊端与风险

- **能力先进性与演进贬值**：基础大模型月月迭代，自研的编排/工具链有被模型原生能力或商业产品快速追平的风险，投入可能 1–2 年后贬值。此维度采购占优（供应商持续跟进前沿）。
- **产品完整度与体验**：商业方案在移动端、协作、可视化、稳定性上是打磨多年的成品；自研短期只能覆盖核心链路（桌面 + 协作层），移动端/多设备/高级可视化要等 2027 甚至更后，体验有代差。
- **组织与协同成本**：两个存量产品可能分属不同 owner，协作层夹在中间，优先级/排期/故障责任要跨团队博弈。"复用"背后是持续的组织协调成本，非采购那种甲乙方边界清晰。
- **人才可持续（bus factor）**：依赖少数既懂两产品、又懂大模型、又懂数据语义的复合人才，人一走知识就走。采购则把这部分能力外包给供应商团队。
- **价值兑现与采纳**：协作/口径统一的价值依赖组织行为改变，非功能上线即兑现，存在"建了没人用"；且"高复用"叙事在争取资源时易被解读成"增量小"。采购有成熟标杆案例背书，内部说服成本反而低。
- **维护与腐化**：语义资产、口径需长期勤勉维护，缺机制会腐化、可信度滑坡。自研要自己扛这份长期运维；采购是供应商扛（但又失去主权，回到锁定问题）。

### 2.5.3 综合对比

| 维度 | 采购第三方 | 自研（整合增强自有资产） |
|---|---|---|
| 数据安全/合规 | ✗ 高风险（数据出域或私有化阉割） | ✓ 本地/内网可控，天然优势 |
| 口径/语义主权 | ✗ 交给供应商，易被绑定 | ✓ 完全自有，是核心资产 |
| 贴合业务 | ✗ 通用产品，定制慢且贵 | ✓ 按公司业务/权限/登录量身做 |
| 供应商锁定 | ✗ 强锁定，议价权低 | ✓ 无外部锁定 |
| 既有投入 | ✗ 浪费 Codata/CodataAdmin 沉没投入 | ✓ 复用增强，边际投入 |
| 能力先进性 | ✓ 供应商持续跟进前沿 | ✗ 有被模型/商业方案追平的贬值风险 |
| 产品完整度/体验 | ✓ 成熟成品（移动/可视化/协作） | ✗ 短期有代差，移动端等后期 |
| 交付速度 | ✓ 采购即用（不含对接） | △ MVP 8–10 周，但有存量底座 |
| 长期 TCO | △ 持续订阅+定制，随规模涨 | △ 人力投入，但资产自有 |
| 组织协同成本 | ✓ 甲乙方边界清晰 | ✗ 跨团队博弈，协调成本高 |
| 责任/风险集中 | ✓ 出事有供应商兜底 | ✗ 自担治理与背书责任 |

### 2.5.4 结论倾向

对**数据敏感、且已有自研存量资产**的公司，采购的两条硬伤——**数据出域合规风险**与**口径主权让渡**——往往是战略级不可接受项，而这恰是自研路线的天然强项。自研的主要代价集中在**能力贬值风险、体验代差、组织协同成本**，这些更多是"可管理的执行风险"，而非"结构性不可控"。

在本项目语境下（已有 Codata + CodataAdmin、数据在内、统一登录在内），自研整合的风险画像明显更可控；采购更适合"没有存量、数据不敏感、要快速见效"的场景。评审中真正要讲清的，是**自研那几条执行风险的应对**——演进保薄层可换、体验分阶段补齐、跨团队 owner 与联合 roadmap 先定——把它们从"隐忧"变成"有计划"（对应 §7.1）。

## 3. 阶段一 · 2026 MVP（协作闭环）

### 3.1 产品功能（用户视角）

1. 以**公司统一登录**身份登录桌面端（CodataAdmin 已实现标准 OAuth2 登录脚手架，改指向公司统一 IDP 即可——见 §3.2），进入团队空间。
2. 分析产出（报告 / 仪表盘 / 结果卡）一键「共享到团队」，团队成员**只读**查看，附带当时的 SQL + **口径标注**（✅ 官方口径 / ⚠️ 自定义未验证——CodataAdmin 已生成的标注）。
3. 复杂会话可被同事 **fork 接力**：继承完整上下文（问题、探索过的表、中间 SQL、错误与修正、结论），用**各自**数据源与模型继续跑，**不泄露原作者凭据**；保留 `forked_from` 溯源与 fork 热度。
4. 团队空间按团队分区 + 搜索发现高价值分析（被 fork 多的即高价值）。
5. 桌面端团队入口：登录态、共享/fork 入口（轻量，不动分析流程）。

### 3.2 实现范围

**做什么**：

- **协作层后端（在 CodataAdmin 内二开）**：
  - 统一资源 ACL 契约（`owner_id` + `acl` JSONB + 团队可见性），挂在 CodataAdmin 现有 RBAC 之上。
  - 「共享到团队」统一动作 + 产物只读查看 + 团队分区 + 搜索。
  - 会话共享 + fork（继承内容不继承凭据）+ `forked_from` 溯源/热度。
  - 口径标注随共享单元传递的传播机制（复用 CodataAdmin 已有口径标注，加传播载体）。
- **登录对接（CodataAdmin 侧，轻改）**：CodataAdmin 已有标准 OAuth2 登录脚手架（现指向飞书）。对接公司统一集成登录 = 改 IDP 端点/凭据/回调 + 建立企业账号↔本地用户映射（沿用 `oauth_feishu_{union_id}` 的自动注册模式，改为按公司 IDP 的稳定标识建用户）。**不是从零做 SSO**，是平移现成脚手架。需公司提供：IDP 类型（OAuth2 / OIDC / SAML / CAS 等）、授权/令牌/用户信息端点、账号唯一标识字段、应用凭据与回调地址。若公司 IDP 非标准 OAuth2/OIDC（如 SAML/CAS），适配工作量上浮，见 §3.3 并行小轨与 §8 决策点。
- **桌面端二开（Codata 侧）**：统一登录态（承接 CodataAdmin 登录会话/令牌）+ 连 CodataAdmin + 共享/fork 入口。
- **对接收口**：桌面端经 CodataAdmin MCP 取数（现状已通），团队资源走 CodataAdmin 新增协作 API。

**不做什么（控范围）**：

- 不 fork 继承凭据 / RBAC 权限化 fork（演进到 2027）。
- 不自建语义层 / 查询编译引擎（2027，且底座已存在）。
- 不 skills 服务端执行（2027）。
- 不共享仪表盘多设备同步（2027）。

**复用什么**：

- CodataAdmin：统一登录(OAuth2 脚手架复用)、RBAC、语义层、MCP、口径优先、readiness、上游变更治理——全部现成。
- Codata：桌面端 + 内嵌后端 + 分析链路——零改动。
- 协作层契约参考 CodataAdmin `Artifact.acl` 模式 + Codata 现有会话/产物存储结构。

### 3.3 开发周期（vibe coding 为主）

复用率高，故周期按"加一层"估算。紧凑 spec→plan→实现小循环，每个子项目一轮。

| 里程碑 | 内容 | 预估 |
|---|---|---|
| M0 协作地基 | 统一资源 ACL 契约 + 团队/可见性字段 + 挂接现有 RBAC + 协作 API 骨架 | ~2 周 |
| M1 共享中枢 | 统一共享动作 + 产物只读 + 团队分区 + 搜索 | ~2–3 周 |
| M2 会话协作 | 会话共享 + fork（继承内容不继承凭据）+ 溯源热度 | ~2–3 周 |
| M3 口径传播 + 联调 | 口径标注随共享传递 + 桌面端登录/共享/fork 入口 + 端到端验收 | ~2 周 |
| **并行轨 · 登录对接** | CodataAdmin OAuth2 脚手架改指向公司统一 IDP + 账号映射 + 桌面端承接登录态 | ~1–2 周（标准 OAuth2/OIDC）/ ~2–3 周（SAML/CAS 等需适配） |

**合计 ~8–10 周，目标 2026 Q4（12 月）MVP 可演示。**（相对 v1 的 ~11–13 周下调——统一登录(OAuth2 脚手架复用)/RBAC/语义层/MCP 全现成，省掉了 v1 的 M0 地基重头。登录对接为并行小轨，不阻塞协作主干——M0–M3 不依赖公司 IDP 落地即可开发，仅在 M3 端到端验收时汇合。）

### 3.4 人力投入

| 角色 | 人数 | 职责 |
|---|---|---|
| 产品 / PM | 1 | owner，兼 spec |
| 后端 | 1 | CodataAdmin 协作层二开 + 登录对接公司 IDP（OAuth2 脚手架平移）+ 桌面端联调 |
| 前端 | 0.5–1 | CodataAdmin 协作 UI + 桌面端轻改 |

### 3.5 POC 可行性评估

| POC | 目标 | 预估 | 验证什么 |
|---|---|---|---|
| POC-1 协作地基可信 | 在 CodataAdmin 加一套资源 ACL + 一个占位协作 API + deny-by-default | 1 周 | 协作层能挂在成熟底座上 |
| POC-2 协作闭环可信 | 一个真实分析 → 共享产物只读 + fork 接力跑通（fork 不继承凭据） | 1–2 周 | 痛点（沉淀、接力）可解 |
| POC-3 口径传播可信 | 一次核心指标查询命中 CodataAdmin 口径 + 标注 + fork 后标注仍在 | <1 周 | 痛点（口径随共享可见）可解 |

**POC 结论**：三项均为"在成熟底座上加层"，复用率高、风险低。建议 MVP 前先跑 POC-1/2 兜底决策；总成本约 3–4 周，可并行/叠入 M0–M1。登录对接不进 POC（脚手架已验证可用，风险在"公司 IDP 协议是否标准 OAuth2/OIDC"这一外部输入，见 §8）。

## 4. 阶段二 · 2027 完整版（语义层深化 + 企业级治理）

### 4.1 产品功能

1. **结构化查询自动编译**：点选维度/指标即可生成跨表查询，agent 不必手写 JOIN（CodataAdmin 受控 JOIN 编译已有一跳，深化为多跳 + chasm/fan trap 处理 + 接 KTX 风格引擎）。
2. **团队口径库**：把验证过的自造 SQL「盖章」为团队认可口径，与官方口径同等优先复用（复用 MVP 共享基础设施）。
3. **skills 集中管理 + 服务端执行**（沙箱 / 资源隔离），桌面端拉取。
4. **共享仪表盘 / 会话云端化**、多设备同步。
5. **权限化 fork**：fork 继承"能跑" + RBAC 校验，以同事自己身份访问数据源（有权限开箱即用，无权限提示）。
6. **治理自动化**：orphan 漂移巡检、知识矛盾检测复核队列、查询成本/审计可观测深化。
7. 业务域标签分类、完整 RBAC 治理、裸 SQL 审计深化。

### 4.2 实现范围

**做什么**：

- 查询编译引擎深化（多跳 JOIN + chasm/fan trap + 结构化查询自动编译，参考 6 层设计 L3 + go-live P5）。
- 口径库盖章机制（复用 MVP 共享 ACL 基础设施，不另造系统）。
- skills 集中存储 / 版本 / 权限 + 服务端执行 worker。
- 仪表盘 / 会话云端化 + 多设备同步（access + refresh token）。
- 权限化 fork + 连接器框架扩展多数据源。
- 治理增强：orphan 巡检、矛盾检测、查询审计深化。

**复用什么**：继续复用 Codata 桌面端 + CodataAdmin 全底座（6 层语义、MCP、检索、上游变更、裸 SQL 审计、readiness 均已就位，2027 是深化而非新建）。

### 4.3 开发周期

## 5. 语义模型维护能力（基于 CodataAdmin 真实能力，已补实）

> v1 此处为占位待材料。现基于 CodataAdmin 仓库补实，不再占位。

### 5.1 维护对象（6 层，已落地）

| 层 | 维护对象 | 落点 |
|---|---|---|
| L1 物理目录 | 库/表/列/分区 | `cat_*` 表，从 DataSage 同步或直连采集 |
| L2 业务层 | 业务实体 + 业务字段（含枚举/可见性/计算表达式） | `sem_entity` / `sem_field` |
| L3 模型层 | 实体间 JOIN 关系（有向图） | `sem_join` |
| L4 维度层 | 分析视角 + 维度↔字段绑定 | `sem_dimension` / `sem_dimension_binding` |
| L5 指标层 | 指标 + 权威口径 SQL（原子/派生/复合，多口径）+ 可用维度白名单 | `sem_indicator` / `sem_indicator_impl` |
| L6 知识层 | 业务背景/口径由来/使用说明/避坑/查询范式（Markdown + frontmatter） | `sem_knowledge` / `sem_knowledge_ref` |

### 5.2 维护动作（已落地 / 深化）

- **注册/编辑/版本/发布**：状态机（草稿→待审→发布→归档）+ 发布快照 + 完整度灯 + 一键发布 + `snapshot_audit` 守卫（拦"引用了模型未声明的列"）。✅ 已落地。
- **口径治理**：口径优先命中 + 自造标红 + `caliber` 口径声明随结果返回。✅ 已落地。
- **上游变更治理**：catalog 同步检出绑定失效/口径 SQL 失效 → 进待办，逐条处理（`bound`/`sql_ref`/`table_only`），忽略必写原因，进 `readiness` blocker。✅ 已落地。
- **裸 SQL 审计**：`execute_sql` 旁路 90 天留痕 + 独立权限点 + 按调用方筛选。✅ 已落地。
- **检索治理**：别名/全文/向量三路 + RRF + 同义词治理 + `did_you_mean`。✅ 已落地。
- **MCP 令牌治理**：签发/轮换/吊销 + 模型级用户隔离 + 调用方留痕。✅ 已落地。
- **就绪自检**：`readiness` + blockers 一键诊断。✅ 已落地。
- **盖章口径库**（2027 深化）：把验证过的自造 SQL 盖章为团队认可口径。

### 5.3 与两阶段关系

- **2026 MVP**：语义模型维护能力**直接复用 CodataAdmin 现成能力，不在 MVP 投入**。MVP 只需保证口径标注能随共享单元传递（§3.2）。
- **2027 完整版**：深化查询编译、口径库盖章、治理自动化（§4.2），均为在现成底座上演进。

### 5.4 待澄清（部署侧，非能力侧）

能力已就位，剩余是部署/治理归属问题：

- CodataAdmin 的运维归属与指标/维度**覆盖广度**（当前覆盖多少业务域/指标，需评估扩展工作）。
- CodataAdmin 与 DataSage 的分工：语义层是否最终完全由 CodataAdmin 承接、DataSage 退为数仓（设计文档标注"暂不考虑与 DataSage 重复建设"，需定边界）。
- 口径维护权限归属（谁有权盖章 = 数据信任的根）。

## 6. 开发方法：vibe coding 怎么做 + 质量兜底

- **紧凑 spec→plan→实现循环**：每个子项目一轮 spec + plan + 实现，用 Claude Code / Codata 自举；复用优先，能用 CodataAdmin / Codata 现有模块不重写。
- **契约先行**：协作层资源 ACL、权限字符串、deny-by-default 在 M0 固化，后续子项目只"填空"不"改地基"。
- **质量兜底（vibe coding 的风险点）**：
  - **前后端契约漂移**：CodataAdmin 前后端契约测试 + 桌面端 TS 类型同步兜底。
  - **安全边界（数据离开本机）**：deny-by-default + 测试 + 评审 checklist；复用 CodataAdmin 已有只读守卫 + 自动 LIMIT + EXPLAIN 预检。
  - **fork 凭据泄露**：不继承凭据是硬约束，需测试覆盖（原作者 datasage token / provider key 绝不随会话泄露）。
  - **两套系统对接漂移**：Codata（Next.js + 内嵌 FastAPI）与 CodataAdmin（Vue3 + FastAPI）栈不同，协作 API 契约要明确定义并测住。

## 7. 风险与缓解

> 说明：Codata 与 CodataAdmin 均为公司**自研存量产品**（Codata 以 Apache-2.0 开源但主导权在我方，CodataAdmin 为内部平台）。因此本路径本质是"**整合并增强自有资产**"，而非"基于外部开源二开"——不存在"无法主导上游"的问题，但会引入下列整合类风险，需在决策评审时正视。

### 7.1 战略 / 组织 / 产品层面风险

| 风险 | 为什么是风险 | 应对方向 |
|---|---|---|
| 产品心智"缝合"感 | 桌面 agent + Web 语义平台 + 中间协作层，对外易被看成"两个工具 + 一层胶水"，而非一个旗舰 data agent；品牌、入口、汇报叙事难统一 | 明确对外单一产品定位与统一入口叙事；协作层做成"无感衔接"而非第三个界面 |
| 路径依赖、迁就存量形态 | 为复用既有形态（桌面 + Web 后台），放弃重新设计更优统一形态的机会；短期省力，长期被存量架构与交互范式绑住，产品张力受限 | 定期评审"复用 vs 重构"边界；对体验割裂处预留统一化演进位 |
| 跨团队归属与协调成本 | 两个存量产品可能分属不同 owner，协作层夹在中间；优先级、排期、故障责任、演进节奏需跨团队博弈，非本项目单方可定 | 尽早明确三方 owner 与联合 roadmap 机制（§8 决策点 3）；协作层模块与接口解耦，减少互相阻塞 |
| "高复用"价值叙事偏弱 | 高复用是省成本卖点，但向上汇报/争取资源时也易被解读为"增量少、没做新东西" | 用"用户价值增量（沉淀/接力/口径可信）"而非"代码量"讲价值；量化采纳率与决策改善 |
| demo 到日常采纳的鸿沟 | 协作价值本质依赖组织行为改变与文化（愿共享、愿接力、信口径），非功能上线即兑现，存在"建了没人用" | 选高意愿业务线做灯塔；配运营/激励；把采纳率、复用率、fork 热度设为北极星而非"交付即结束" |
| 语义资产持续腐化 | 口径可信、查询准确高度依赖语义模型覆盖广度与维护勤勉度；维护是长期投入，缺机制则随业务变化腐化，可信度滑坡 | 把语义维护做成常设职能与流程（owner + 巡检 + 上游变更治理），而非一次性建设（见 §5） |
| 大模型演进致自研贬值 | 赛道随基础模型月月迭代，今天自研的编排/工具链可能 1–2 年内被模型原生能力或成熟产品覆盖 | 自研聚焦"公司专属资产"（语义口径、协作沉淀、权限）；可替代的通用能力保持薄层、可换 |
| 治理与信任的组织级红线 | agent 能查数、执行 SQL、跨团队共享结论；数据权限、合规、结论权威性敏感，错误口径经 fork 扩散会放大错误决策 | 口径盖章/背书责任制；跨团队共享走 RBAC + 审计；高风险结论标注可信度与出处 |
| 人才可持续（bus factor 低） | vibe coding + 小团队，依赖少数懂两产品 + 大模型 + 数据语义的复合人才，流失即知识流失 | 关键设计文档化 + 结对，避免单点；spec/plan 沉淀降低 onboarding 门槛 |

### 7.2 执行 / 技术层面风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 两套系统栈差异 | Codata(Next.js+内嵌FastAPI) vs CodataAdmin(Vue3+FastAPI+MySQL)，协作契约需跨栈对齐 | 协作 API 契约先行 + 契约测试；桌面端只经 MCP + 协作 API 两通道对接 |
| CodataAdmin 运维归属 | 语义层 + 协作层都压在 CodataAdmin，单服务责任重 | 明确运维 owner（§8 决策点 3）；协作层与语义层模块隔离，独立部署/扩缩容预留 |
| 两个自研产品并行演进 | 二开改动与 Codata / CodataAdmin 各自主线并行迭代，需版本协调（二者均为我方产品，无外部上游同步问题） | 统一版本节奏 + 二开改动模块化，减少与主线冲突；维护改动清单便于回灌主线 |
| vibe coding 质量 | 契约漂移、安全边界被破 | 契约测试 + 安全边界测试（§6 质量兜底）+ 关键路径人工验收 |
| DataSage/CodataAdmin 边界不清 | 语义层重复建设或口径双轨 | §5.4 定边界：CodataAdmin 承接语义层，DataSage 退为数仓（§8 决策点 4） |
| 2027 查询编译引擎 | 最大技术风险（结构化查询自动编译） | 底座（一跳 JOIN + 拒绝规则）已就位，先 POC 再投入 |
| 公司统一登录依赖外部 IDP | 登录节奏取决于公司 IT 提供 IDP 协议/凭据/回调的时点与协议标准度（标准 OAuth2/OIDC 轻量，SAML/CAS 上浮） | 脚手架已现成、可平行轨；M0–M3 不依赖 IDP 落地，M3 验收时汇合；早期确认公司 IDP 协议（§8 决策点 7） |
| 账号映射错位 | 多套登录来源（飞书/公司 IDP/本地）混用导致同人多账号 | 以公司 IDP 稳定标识为唯一主键建用户；已有飞书账号做一次性映射/合并，避免口径归属与 ACL 错挂人 |

## 8. 决策点 / 待澄清

1. **后端主体确认**：是否锁定"以 CodataAdmin 为后端主体、不另起 codata-server"（v2 方向）？这放弃 v1 的官方 full-stack-fastapi-template 选型，换取统一登录/语义层/MCP 全现成。
2. **MVP 是否落在 2026 Q4（~2–3 个月）？** 若要更宽 scope（如含 fork 继承凭据），顺延 2027 Q1。
3. **CodataAdmin 运维归属**：语义层 + 协作层均压其上，需定 owner 与 SLA。
4. **DataSage 与 CodataAdmin 边界**：语义层最终由谁承接（§5.4）。
5. **桌面端二开形态**：当前按"复用为主、可回灌"推进；是否需进一步约束 fork 同步策略。
6. **fork 是否需提前支持"继承凭据"**：影响安全边界与节奏，默认留 2027。
7. **公司统一登录对接**：需公司/IT 提供——IDP 协议类型（标准 OAuth2 / OIDC 可直接复用脚手架；SAML / CAS 需写适配层，工作量上浮）、授权/令牌/用户信息端点、应用凭据与回调地址、账号唯一标识字段。该输入决定 §3.3 并行轨工期与账号映射方案，建议 MVP 启动前尽早向 IT 澄清。
