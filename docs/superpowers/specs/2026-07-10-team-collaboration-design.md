# Codata 企业级协作层 —— 设计文档

- 日期:2026-07-10
- 状态:设计(brainstorming 产出,待用户评审)
- 落地位置:**codata-server(独立远程后端)**,依赖 [2026-07-08 codata-server 蓝图](./2026-07-08-codata-server-blueprint-design.md)
- 范围界定:本文档只定义**产品协作方向**;SSO 登录、团队模型、RBAC、权限判定由用户自有脚手架承载,不在本文范围内。

---

## 1. 背景与目标

Codata 要从"个人 local-first 的 data agent"演进为"企业内团队共用的通用 agent + data agent"。用户已明确:

- **租户模型 = 单企业、多团队软隔离**(A 类)。团队用于划分资源可见范围,**不做跨组织硬租户隔离**。
- **身份源 = 飞书为主。** SSO / 团队 / RBAC / 权限判定均由用户已有脚手架处理,本设计不重复定义。
- 本设计聚焦一件事:**Codata 作为团队共用 agent,"协作"与"共享"在产品层面怎么设计才好用。**

协作被拆成三类能力,按用户排定的优先级推进:

1. **③ 异步协作(接力 / 求助)** —— 最高优先
2. **① 沉淀复用(团队资产)** —— 次高优先
3. **② 口径与信任(数据一致性)** —— 第三优先

三者共享同一套底层"共享"基础设施,并落在 codata-server 蓝图 §5.4 的"统一资源 ACL 契约"这块地基上。

---

## 2. 核心抽象:「共享到团队」是一个统一动作

任何可共享单元通过**同一个"共享到团队"动作**进入团队空间,底层是同一套共享基础设施(owner_id + acl + 团队归属),区别只在**被共享对象的打开方式**:

| 共享单元 | 打开方式 | 性质 |
|---|---|---|
| **产物**(report / 仪表盘 / 结果卡) | 团队**只读**查看快照,附带当时的 SQL + 口径标注 | 终态 |
| **会话** | 团队可 **fork 分叉**,基于它继续问自己的 | 可延续态 |

这一抽象直接对应 codata-server 蓝图里"每个共享资源遵循同一套 `owner_id` + `acl`(JSONB)+ 团队可见性"的契约——协作层是往那份契约里"填空",不新造地基。

---

## 3. ③ 异步协作(接力 / 求助)—— 最高优先

### 3.1 共享动作的两种落点

- **发布产物** → 团队空间出现一张**只读卡片**,任何人可查看其 SQL + 口径标注。
- **共享会话** → 团队空间出现一个**可 fork 的会话入口**。

### 3.2 Fork 语义(首期 = 继承内容 + 溯源)

- **继承内容,不继承凭据(首期落地项)**:同事 fork 后拿到完整对话历史——问过什么、agent 探索过哪些表、中间 SQL、错误与修正、结论。但**继续跑时用他自己的数据源连接和模型 key**。原作者的 datasage token / provider key **绝不随会话泄露**。
  - 代价:同事需先配好自己的数据源,否则 fork 后跑不动——首期可接受,以安全边界清晰为先。
- **保留 `forked_from` 溯源(首期落地项)**:新会话记录"fork 自 XX 的会话";原作者能看到自己的分析被 fork 了几次。此热度信号顺带喂养 ①(见 §4.2)。

### 3.3 演进预留

- **fork 继承"能跑" + RBAC 权限校验**:继续跑时以同事**自己的身份**去访问数据源——有该数据源权限就开箱即用,没有则提示"需先获得 X 数据源访问权"。对应蓝图讨论中的 C 方案。等连接器权限 / RBAC 就位后再上。fork 传递的是**知识**,不是越权通道。

---

## 4. ① 沉淀复用(团队资产)—— 次高优先

核心问题:共享出来的东西堆在一起,同事怎么**找得到、信得过**。光有共享动作不解决发现问题,团队空间会变成没人看的垃圾堆。

### 4.1 组织方式:按团队分区

- 共享默认落到**本团队**空间。
- 可选**提升到全公司**可见。
- 每个共享单元带一个**团队归属**字段,直接挂在用户已有的团队脚手架上。

### 4.2 发现能力(横切,不管怎么分区都要有)

- **搜索**:按标题 / 内容 / SQL 检索已共享的产物和会话。
- **fork 热度**:被 fork 多的会话 = 团队高价值资产,用于排序 / 标记(直接复用 ③ 的 `forked_from` 计数)。

### 4.3 演进预留

- **业务域标签**(如 增长 / 营收 / 留存):分区之上的轻量补充,共享时可打域标签,跨团队按业务域找。分区不够用时再加,首期不强上目录。

---

## 5. ② 口径与信任(数据一致性)—— 第三优先

data agent 的团队命门:"到底哪个数是对的"。Codata 已接 datasage,其语义层自带"注册指标 + 验证过的口径 SQL"。② 的关键不是从零造口径系统,而是让 **agent 生成的 SQL 与官方口径的衔接可信、可见**。

### 5.1 首期 = 口径优先 + 自造标红

- agent 优先命中 **datasage 已注册指标**(团队验证过的官方口径),命中即标 **✅ 官方口径**。
- 查不到注册指标才自造 SQL,并显眼标 **⚠️ 自定义口径,未经验证**。
- 口径标注**随共享一起传递**:③ 甩出去的会话、① 沉淀的产物,都自带可信度标签,让"这个数对不对"一眼可见。

此方向与 README 现有的 "metric caliber discipline" 一致;首期主要工作是把标注做得更显眼、并确保它随共享单元传播。

### 5.2 演进预留

- **团队自攒口径库**:把某人验证过的自造 SQL "盖章"为"团队认可口径",下次同类问题优先复用,盖章的与官方口径同等优先。它本质是 ①(沉淀复用)在"口径"这一资产上的特例——直接复用共享机制,**不单独造系统**。

---

## 6. 依赖与边界

- **依赖** codata-server 蓝图(2026-07-08)的:统一资源 ACL 契约、deny-by-default 鉴权网关、团队可见性字段。协作层是那份契约的填充。
- **不属于本设计**(由用户脚手架承载):飞书 SSO 登录、团队的建立与成员管理、RBAC 角色与权限判定。
- **不改动**现有桌面端内嵌 sidecar 后端;共享资源存放在 codata-server 的独立存储(Postgres),不进桌面端 SQLite。

---

## 7. 优先级与落地顺序小结

| 优先级 | 能力 | 首期落地 | 演进预留 |
|---|---|---|---|
| 1 | ③ 异步协作 | 统一共享动作 + 会话 fork(继承内容不继承凭据)+ `forked_from` 溯源 | fork 继承凭据 + RBAC 校验 |
| 2 | ① 沉淀复用 | 按团队分区 + 搜索 + fork 热度 | 业务域标签 |
| 3 | ② 口径信任 | 口径优先命中 + 自造标红 + 标注随共享传递 | 团队自攒口径库 |

每一项后续各自走一轮 spec → plan → 实现;共享基础设施(§2 的统一动作 + ACL 契约)是三者共同的地基,应先落地。
