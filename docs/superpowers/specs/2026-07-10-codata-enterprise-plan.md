# Codata 企业化建设计划书

- 日期:2026-07-10
- 状态:汇报稿(供决策评审)
- 汇报对象:管理层
- 一句话:把 Codata 从"个人本地数据 agent"升级为"团队共用的企业级通用 agent + data agent",新增一个统一后端服务承载团队身份与协作。

---

## 一、为什么做(现状与痛点)

Codata 目前是**本地优先的单人桌面工具**:每个人的会话、仪表盘、分析结果都只存在自己电脑上。它已经能做自然语言问数、自动发现表和指标、生成并执行 SQL、出图表和报告。

但作为**团队工具**,今天有三个硬伤:

1. **产出无法沉淀** —— 一个人做完的分析,别人看不到,每人都得重新问一遍 agent,重复劳动。
2. **无法接力协作** —— 想把一段分析甩给同事继续、或求助,只能截图/复制,上下文全丢。
3. **数据口径不统一** —— 同一个问题不同人问,可能得到不同的 SQL、算出不同的数,团队缺乏"哪个数是对的"的共识。

根因是**缺少一个团队共享的中枢**:没有统一登录、没有团队身份、没有共享资源的地方。

---

## 二、做成什么样(目标)

- **单企业自托管、团队共用**。飞书登录(SSO),一套团队/角色/权限体系。
- 新增一个**统一后端服务 codata-server**,作为团队身份权威和共享资源中枢。
- 让个人的分析产出能**沉淀成团队资产、能接力协作、口径可信可追溯**。
- **桌面端体验不倒退**:现有本地工具照常用,联网后多出团队协作能力。

**明确不做**(控制范围与成本):
- 不做面向多家公司的多租户 SaaS(只服务自己企业)。
- 不推倒现有桌面端重做(新服务是增量,不是替换)。
- 首期不追求功能大而全,先把"地基 + 最痛的协作"跑通。

---

## 三、整体架构(要新增什么、动什么)

```
┌─────────────────────────┐     ┌─────────────────────────┐
│  桌面端(现有,基本不动) │     │  Web 管理台(新增)      │
│  分析师日常问数/分析      │     │  团队/用户/共享资源运营   │
└───────────┬─────────────┘     └───────────┬─────────────┘
            │  飞书登录后带令牌               │  飞书登录后带令牌
            └───────────────┬───────────────┘
                            ▼
              ┌──────────────────────────┐
              │  codata-server(新增)     │  ← 本次建设主体
              │  · 飞书 SSO 登录 + 令牌     │
              │  · 团队 / 角色 / 权限(RBAC)│
              │  · 共享资源中枢(会话/产物)│
              │  · 口径标注随共享传递       │
              └────────────┬─────────────┘
                           ▼
                    ┌────────────┐
                    │ Postgres   │  ← 新服务独立数据库
                    └────────────┘

外部数据源:datasage(现有,通过 MCP 接入)、其他数仓(后续)
```

**三端分工:**

| 端 | 状态 | 职责 |
|---|---|---|
| 桌面端(Tauri + Next.js + 内嵌后端) | **现有,基本不动** | 分析师问数、分析、消费团队共享 |
| Web 管理台 | **新增** | 团队/用户/权限、共享资源运营维护 |
| codata-server | **新增,本次主体** | 团队身份权威 + 共享资源中枢 |

**技术选型(已定):** 官方 full-stack-fastapi-template(FastAPI + Postgres + 自带 React 管理台前端),与团队 datasage 平台同一套技术栈,人员和模式可复用。

**改动量说明:**
- **新增**:codata-server 后端、Web 管理台、Postgres 数据库。
- **小改**:桌面端增加"飞书登录 + 连团队服务 + 共享/fork 入口",不改核心分析流程。
- **不动**:现有桌面端的本地分析能力、内嵌后端、datasage 集成。

## 四、核心能力设计

### 4.1 统一登录与团队(地基)

- 飞书扫码登录(SSO),团队/角色由飞书组织架构 + 脚手架承载。
- 一套"谁是谁、什么角色、能碰什么"的权限体系(RBAC:管理员 / 分析师 / 查看者)。
- 所有共享资源遵循统一契约:**归属人 + 团队可见性 + 访问控制**。

### 4.2 「共享到团队」—— 一个统一动作

任何东西通过同一个"共享到团队"动作进入团队空间,只是打开方式不同:

- **产物**(报告 / 仪表盘 / 结果卡)→ 团队**只读**查看,附带当时的 SQL 和口径标注。
- **会话**→ 团队可 **fork 分叉**,基于它继续问自己的。

### 4.3 三大协作能力(按优先级)

| 优先级 | 能力 | 首期做什么 | 解决的痛点 |
|---|---|---|---|
| **1** | **异步协作(接力/求助)** | 共享会话可被同事 fork;fork 继承完整上下文(问题、探索过的表、SQL、结论),但用同事自己的数据源/模型跑(不泄露原作者凭据);记录"fork 自谁",可追溯 | 痛点 2:接力协作 |
| **2** | **沉淀复用(团队资产)** | 共享资源按团队分区(默认本团队,可提升全公司);支持搜索;被 fork 多的即高价值资产 | 痛点 1:产出沉淀 |
| **3** | **口径信任(数据一致)** | agent 优先命中 datasage 官方指标口径并标"✅ 官方口径",自造 SQL 标"⚠️ 未验证";标注随共享传递,一眼可见数对不对 | 痛点 3:口径统一 |

**后续演进**(不在首期,但地基已预留):fork 按权限直接复用数据源、业务域标签分类、团队自建口径库、共享仪表盘/会话多设备同步、skills 集中管理与服务端执行。

## 五、分阶段路线图

每个阶段是一个可独立交付、可演示的里程碑。

| 阶段 | 内容 | 产出 | 依赖 |
|---|---|---|---|
| **P0 地基** | codata-server 骨架:飞书登录 + 用户/团队/角色 + 权限网关 + 统一资源契约 + Web 管理台登录/用户页 | 能登录、能管人、地基就位 | 无 |
| **P1 共享中枢** | "共享到团队"统一动作 + 产物只读查看 + 团队分区 + 搜索 | 分析产出能沉淀、能被找到(痛点1) | P0 |
| **P2 会话协作** | 会话共享 + fork(继承内容不继承凭据)+ fork 溯源与热度 | 能接力、能求助(痛点2) | P1 |
| **P3 口径信任** | 口径优先命中 + 自造标红 + 标注随共享传递 | 数据口径可信可见(痛点3) | P1 |
| **P4+ 演进** | 权限化 fork、口径库、共享仪表盘、skills 服务化等 | 按需排期 | 各自依赖 |

> 说明:P2 和 P3 都只依赖 P1,可并行或按资源情况调序。P0 是一切的前提。

---

## 六、汇报要点(给领导的三句话)

1. **做什么**:新增一个团队后端服务(codata-server)+ Web 管理台,让 Codata 从个人工具变成团队共用的企业 agent,飞书登录、统一权限。
2. **动多少**:主要是"新增",现有桌面端基本不动、不推倒重来;技术栈与现有 datasage 平台一致,风险可控。
3. **怎么落地**:先建地基(登录/权限/共享契约),再按"沉淀 → 协作 → 口径"三步交付,每步都能独立演示见效。
